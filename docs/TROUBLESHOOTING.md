# 遇到的问题与解决方案

当前结构见 [ARCHITECTURE.md](ARCHITECTURE.md)，设计变动见 [DECISIONS.md](DECISIONS.md)。本手册区分“代码已有防护”与“对应关卡实测已通过”；二者不能互换。

## 先判断运行停在哪里

```bash
# 选择你实际运行的目录，不要拿历史报告代替当前会话。
RUN=pokemon/runs/<会话目录>
cat "$RUN/report.json"
grep -E '"type": "(planner_configuration|planning_requested|plan|plan_outcome|planning_error|jev_wait|finished)"' "$RUN/events.jsonl" | tail -30
```

| 现象/状态 | 含义 | 先做什么 |
| --- | --- | --- |
| `blocked_missing_key` | Jev 密钥没有进入游戏进程 | 检查本机配置；不要粘贴密钥到日志/聊天 |
| `blocked_missing_planner_key` | 严格双模型模式缺 DeepSeek 密钥 | 检查实际启动环境；云端 Secret 不等于本机 `.env` |
| `planner_unavailable` | 规划请求、响应或合同失败 | 看 `planning_error` 的错误类型/HTTP 状态，检查端点和账户实际支持的模型 |
| `waiting_for_jev` | 模拟器暂停等待 Jev 恢复 | 查看重试事件；画面不动不是自动判定游戏策略卡住 |
| `planner_budget_reached` / `time_budget_reached` / `budget_reached` | 达到相应预算后停止 | 从有效 checkpoint 继续，不记作成功 |
| `stalled` | 有界恢复后问题仍在 | 保存完整旁文件与最后一段事件，定位规划和执行哪一层失败 |
| `completed` | 代码观测到规定的终局验收证据 | 检查 `game_completed` 和终局证据；模型文字宣称不算 |

`planning_calls` 是请求次数，`plans` 是通过校验的计划数，`jev_calls` 是接受的 Jev 决策数，`executed_actions` 是实际输入次数。不要用其中一个代替另一个，也不要只看 CI 绿色。

## 已遇到并处理的问题

### P01 · FireRed 能下载，但旧模拟器/读取器根本不支持

**根因：** GBA FireRed 与 GB Red/Red Star 是不同平台；第三方 FireRed reader 当时只有占位实现。更换文件名不能修复平台和地址表差异。

**处理：** 当前只支持固定 Red Star 的 PyBoy 适配与哈希检查。FireRed 和旧尝试从当前源码树移除；不会根据扩展名自动猜 reader。更换游戏属于单独适配工作。

### P02 · Red Star 能开机，但不能因此沿用原版 Red 地址

**根因：** 文件内部标题、内容哈希与原版 Red 不同；历史源码重建也非逐字节一致。

**处理：** 使用独立 `redstar-profile.json`，区分来源先验与实际结构/签名/动作响应验证。保留原版校验边界，不直接把改版加入原版白名单。空队伍读取的成功不自动验证非空队伍。

### P03 · PyBoy 读空切片报错

**根因：** 模拟器内存切片与普通 Python `bytes` 的空范围行为不同。

**处理：** `Emulator.read(..., length=0)` 直接返回 `b""`，范围先校验；对应纯测试保留在 `pokemon/tests/test_core.py`。

### P04 · 原地反复按 A 或 WAIT

**根因：** 旧文本框/菜单 RAM 值可能残留；地形 tile 与字体共享编号；“空文本”不意味着在加载。早期 12 步运行有 9 次 A、3 次 wait，坐标不变。

**处理：** 先识别场景，再解码文本；野外地形不当对白。记录对话打开/关闭、重复交互和近期前后状态，提示等待仅用于有证据的动画/打印。历史原地循环是失败记录，不是当前进展。

### P05 · 回归断言期待 ITEM，但改版菜单实际显示 PACK

**根因：** 把原版界面文字当成改版事实。

**处理：** 以真实 Red Star 菜单和游标变化验证识别，不用原版字符串覆盖画面。旧一次性截图和脚本已退出当前树，核心场景/输入合同测试仍保留。

### P06 · 已选初始宝可梦，却误报队伍结构损坏

**根因：** 昵称确认过程中 party count 已增长，但最后一个成员结构尚未初始化。

**处理：** 用准确的 ROM 调用位置与命名状态区分“待登记”与“坏结构”；此阶段不宣称已有可战斗队员，也不因为临时零值直接终止。

### P07 · 训练师开场无限等待双方 HP 初始化

**根因：** 完整挑战对白需要先按 A，战斗双方结构随后才初始化；等待数据就绪再确认会形成死锁。战斗文本也不完全沿用野外文本框标记。

**处理：** 战斗阶段与双方数值分别验证；已完成挑战对白可推进，未验证数值保持未知。当前 battle strategy 不得用无效 HP 做伤害比较。

### P08 · 地图切换瞬间写入错误位置；地图级 BFS 跳过洞穴

**根因：** 转场时地图 ID/尺寸/坐标未必同时更新；同一地图包含多个不连通区域，单向台阶也不是双向边。

**处理：** 未对齐观察不写永久地形；用“地图＋区域”路由，保留出口落点和方向，柜台交互站位单独处理。当前仍是有限范围的地形先验，不包含所有剧情条件。

### P09 · 战败返程被当成停滞；或者一直活动却没有主线收益

**根因：** 只用新坐标评估进展会误停正常返程；只看 HP/文字变化又会漏掉长周期循环。

**处理：** `ProgressTracker` 与 `StallMonitor` 分别统计探索、剧情与可观察活动。箭头闪烁不算进展。保留已知路线活动的合成回归，不把它当真实战斗成功。长周期回城/练级循环仍需结合计划结果、资源净变化判断。

### P10 · CampaignPlanner 已给答案，Jev 却被要求重复判断

**根因：** 固定剧情、导航和战斗建议都由代码包办，Jev 容易只成为最后一层按键重选。

**处理：** 双模型模式让 DeepSeek 产生短期计划，CampaignPlanner 管理状态/验收，Jev 处理局部输入。当前未切换成程序自动走路径；这是仍保留的效率权衡，不应冒称问题完全消失。

### P11 · DeepSeek 只是卡住顾问，错误计划只能等超时

**根因：** 初版只在停滞时调用；存在任何计划就禁止重规划；`complete_when` 在规范化后丢失，`milestones` 字符串没有验收执行。

**处理：** 引入 `plan_contract.py`，保存并执行 `success` 条件，分别处理完成/失败/失效/到期；启动和无有效计划时规划。旧格式计划失效后重建；结束结果反馈给下一轮。对应 `test_plan_lifecycle.py` 保留。

### P12 · 规划器猜坐标，或者看不到导致卡关的对白

**根因：** 只给地图名、HP 和循环计数，遗漏对象、出口、导航诊断；仅检查 JSON 字段类型允许无效坐标进入路径计算。

**处理：** 共用观察质量过滤，发送现场及失败结果；只允许本次 `target_ref`，程序解析真实位置。规划需要的信息应足够解释错误，不能期待大模型补出没收到的证据。

### P13 · 治疗与过山计划互相指挥；恢复抹掉地图

**根因：** 规则治疗覆盖目标，但模型意图又被加回 `current_focus`；恢复时整图清空使同一失败重试。部分资源字段只存储未消费。

**处理：** 紧急治疗暂停计划与 TTL，单一意图生效；恢复保留探索地形，允许动态信息修正；接通资源阈值、捕获目标/队伍上限。计划有效不等于保证资源策略最佳。

### P14 · 配了 DeepSeek，但云端仍是零次请求

**根因：** 本机 `.env`、现有进程环境与 GitHub Secrets 是不同环境；Secret 必须显式注入。旧绿色测试运行也可能完全跳过游戏步骤。

**处理：** 严格模式明确报错，记录配置、请求、接受计划和动作次数；两把密钥脱敏。修改 `.env` 后结束旧进程再恢复。目前 CI 已改为纯代码验证，不再提供含密钥的游戏作业；游戏运行使用本地入口。

### P15 · 运行了看不到结果；evidence/archive 不断膨胀

**根因：** 无窗口模拟器不会弹窗；早期只有零散 JSON/PNG。后续 publisher 又把每轮回放自动提交到源码树。

**处理：** 保留只读 HLS/SSE 网页及可选离线导出器；移除静态历史回放、自动 publisher 和写仓库的 CI 作业。结果只在忽略目录生成。Git 保留可维护结论，不存每轮截图。

### P16 · 视频短暂停顿导致误终止，或视频与手柄显示不同时

**根因：** 编码器和模型线程的节奏不同，单次慢写不等于持续卡死；HLS 天然有缓冲。

**处理：** 视频健康按连续写入进展判断，允许有界重启，终态仍明确记录。手柄依据真实 `executing` 事件，补发历史不冒充新输入；看状态/事件定位，不能只凭视频延迟判断按键失败。

## 月见山：尚未闭合的效果验证

用户观察到的“昨天卡在月见山”不能由出生房间回归替代。已提交的双模型修复测试包含合同与真实 ROM 基础验证，但当时双模型云端尝试因缺 DeepSeek 密钥而为零次模型动作；没有形成通过月见山的证明。参见 [PR #2](https://github.com/atrl/pokemon-jev-readable/pull/2)。

| 实际尾部轨迹 | 重点检查 |
| --- | --- |
| 导航建议正确，Jev 反复偏离 | 当前意图冲突、场景识别、候选说明和模型选择 |
| Jev 选了建议方向但没有移动 | 碰撞/NPC、转场锁、方向先转身、输入时序 |
| 楼层来回或总回到同一墙边 | 区域/出口对应、前沿选择、过期或缺失路径证据 |
| 科学家/化石旁反复交互 | 当前对白、剧情前置条件及可执行成功谓词 |
| 遇敌—回城—再遇敌循环 | HP/PP 净消耗、野战策略、补给计划完成与失败历史 |

重试必须保留同一 ROM、`last.state`、manifest 和两份记忆旁文件；比较实际越过目标区域/剧情条件，不只比较动作次数。每次修订固定一个版本，记录模型标识、预算与计划结果。

## 清理后的维护规则

不要提交 `.env`、ROM、存档、原始日志、视频或生成回放。不要为了让 CI 绿色而伪造模型返回或跳过失败声明。核心测试使用显式合成数据和临时目录；缺私有 checkpoint 的可选回归明确跳过。

历史原始验证可从清理前提交 `6c0c35c` 查看，不在当前树保留副本。本次没有重写提交历史；有彻底移除历史大文件/敏感内容的需求时，需另行协调克隆、标签和强制更新，不能把普通删文件说成历史已清除。
